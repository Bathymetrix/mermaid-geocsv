# Audit 1 — reader outcomes and design

Audit completed 2026-10-07 against `mermaid-geocsv` 0.9.0. This records the
independent outcomes audit completed before the prior reports were consulted.
Source links below point to the current files after the metadata classes moved
into `read.py`; that move did not change the behavior described here.

The audit inspected the parser, metadata model, public API, reader specification,
tutorial, tests, bundled GeoCSV examples, and the included
[GeoCSV v2.0.4 specification](../docs/references/GeoCSV_v2.0.4.pdf).
Targeted probes used the repository's `.venv`. The legacy writer and MATLAB
parser were not executed, and behavior against external GeoCSV files or every
supported pandas version was not verified.

The reconciliation checkboxes start unchecked. Checking one means its decision
or change has been completed and verified. A documented decision to retain a
current policy can resolve a design item without changing the parser. This
checklist does not authorize changes beyond the item being reconciled.

## 1. Changed custom scientific metadata can span one table

**Severity and status:** Moderate. Demonstrated behavior; Audit 1 classified
it as a metadata-integrity defect for malformed input. Whether the GeoCSV
boundary rule covers unknown keywords needs an explicit decision.

**Location at audit time:** The comment branch skipped unknown keys before
declaration-change checks. The current reader compares repeated unknown keys
in the comment branch of [`read.py:420`](../src/mermaid/geocsv/read.py#L420).

**Reproducer:**

```text
#dataset: GeoCSV
#GeodeticDatum: WGS84
Latitude
1
#GeodeticDatum: NAD27
2
```

At audit time, the reader returned one two-row table. Both comments survived in
`frame.attrs["geocsv"].comments`, but the table had no row-to-datum association.
GeoCSV v2.0.4 section 8 calls for a new dataset when a keyword value changes;
sections 3, 5, and 7 distinguish known keywords from other comments. The
scope of that rule for custom scientific keys is therefore the design question.

**Focused recommendation:** Decide whether custom `#key: value` comments can
declare dataset-wide scientific metadata. If so, reject a changed value without
a new `#dataset` marker. Keep free-text comments usable between records.

**Reconciliation:**

- [x] Decide and record which custom keyword/value comments, if any, carry
  dataset-wide meaning; consult the format specification and representative
  GeoCSV examples before changing the parser.
- [x] If they are dataset-wide declarations, reject conflicting values within
  one dataset and add a focused test using a scientific key such as
  `GeodeticDatum`.
- [x] Document the chosen rule, including how ordinary free-text comments are
  treated; bump the package version if supported parsing semantics change.

**Resolution (0.10.0):** For any unknown `#key: value` line, the reader accepts
the first occurrence before or after the header and identical repetitions.
It rejects a changed repetition after the header unless a new `#dataset`
section begins. Differing pre-header values are retained, with the last value
used for later comparisons. Free-text comments remain unrestricted. This is a
provisional reader policy; custom-keyword scope remains an
[open specification question](../docs/OPEN_QUESTIONS.md#1-do-custom-keyword-lines-define-dataset-wide-metadata).
Focused rejection and two-dataset tests cover both `GeodeticDatum` and other
unknown keys. The README and reader specification describe the rule.

**Why this policy:** pandas
[`DataFrame.attrs`](https://pandas.pydata.org/docs/reference/api/pandas.DataFrame.attrs.html)
applies to the whole table. Preserving a changed comment in `attrs` does not
associate its value with particular rows. If row-varying custom metadata
becomes useful, the reader could populate an explicit per-record column from
the comment positions, carrying the value forward until the next change. That
would require a defined inheritance rule and a deliberate change to the public
table schema; the GeoCSV specification should settle custom-key meaning first.

## 2. Missing-only datetime columns acquire a UTC dtype

**Severity and status:** Moderate. Demonstrated representation defect in Audit
1's assessment; no non-missing timestamp is changed.

**Location:** [`read.py:345–347`](../src/mermaid/geocsv/read.py#L345)
passes `utc=True` when a datetime column has no non-missing source value.

**Reproducer:** A `datetime` column containing only `nan` and `NaT` is returned
as `datetime64[s, UTC]` with the current pandas environment. The source supplies
no timezone. A column containing a timezone-free timestamp instead has a naive
datetime dtype. A header-only datetime column follows the same UTC branch.

**Focused recommendation:** Use a naive datetime dtype when no source value
establishes a timezone, unless the caller explicitly requested a timezone.

**Reconciliation:**

- [ ] Decide the dtype policy for both all-missing and header-only datetime
  columns, including the case where `datetime_timezone` is supplied.
- [ ] Implement the chosen policy and update the focused dtype tests without
  changing the treatment of non-missing source timestamps.
- [ ] Document any public data-model change and bump the package version.

## 3. Universal `nan` handling can erase literal string data

**Severity and status:** Moderate design risk, demonstrated and already
documented as a deliberate MERMAID policy. It is not an undocumented parser
behavior.

**Location:** [`read.py:526–527`](../src/mermaid/geocsv/read.py#L526);
the current policy is described in
[`READER_SPEC.md:152–166`](../docs/READER_SPEC.md#L152).

**Reproducer:** With `#field_type: string` and `#field_missing: X`, source
values `nan` and `NAN` become `pd.NA` rather than literal labels. A quoted empty
string also becomes missing. The parsed column cannot distinguish those source
values from missing data.

**Focused recommendation:** Decide whether string fields should rely on their
declared missing marker, or whether the format needs a way to express literal
`nan` and empty strings. Treat a change as a public data-model decision.

**Reconciliation:**

- [ ] Confirm whether the existing universal `nan` policy remains intentional
  for string fields, considering source labels that may literally be `nan`.
- [ ] If the policy changes, define the precedence of empty fields, quoted
  empty strings, `nan`, and `field_missing`; update focused tests and public
  documentation, then bump the package version.
- [ ] If the policy stays, record that literal `nan` and quoted empty strings
  cannot be represented in parsed string columns.

## 4. Invalid UTF-8 escapes the documented parser error type

**Severity and status:** Low. Demonstrated error-path defect.

**Location:** [`read.py:154–159`](../src/mermaid/geocsv/read.py#L154)
opens UTF-8 input but wraps only `GeoCSVError`. The
[`read` docstring](../src/mermaid/geocsv/read.py#L148) says malformed or
unsupported content raises `GeoCSVError`.

**Reproducer:** A GeoCSV data row containing byte `0xff` raises
`UnicodeDecodeError`, without the reader's source-located `GeoCSVError` wrapper.

**Focused recommendation:** Wrap decoding failures with the source path and a
`GeoCSVError`, or narrow the documented error guarantee.

**Reconciliation:**

- [ ] Decide whether invalid UTF-8 belongs to the `GeoCSVError` contract.
- [ ] Align code and documentation with that decision; add one focused invalid
  byte probe if the exception contract changes.

## 5. Future GeoCSV versions may be parsed under current rules

**Severity and status:** Low, plausible risk. No incompatible future version
was available to demonstrate an incorrect result.

**Location:** [`read.py:405–408`](../src/mermaid/geocsv/read.py#L405)
accepts any dataset value containing `geocsv`. The
[`reader specification`](../docs/READER_SPEC.md#L99) documents that versions
are not validated.

**Scenario:** `#dataset: GeoCSV 99.0` passes the identity check and is parsed
using the current format rules. If a future version changes those rules, the
result could look valid while carrying the wrong interpretation.

**Focused recommendation:** Define supported container versions when the
package's version policy is settled; retain an explicit decision about the
unversioned `GeoCSV` form used by MERMAID files.

**Reconciliation:**

- [ ] Decide whether the reader should validate container versions, and which
  current versioned and unversioned declarations it must accept.
- [ ] If validation is adopted, add focused acceptance/rejection cases and
  update the reader specification and package version.

## Prior-audit context

The earlier [specification audit](01.md) resolved change checks for **known**
keywords while retaining unknown comments, and deliberately retained universal
`nan` handling. It left version validation open. The later
[adversarial audit](02.md) noted the UTC dtype for empty or all-missing datetime
columns but treated it as a representation policy. Those historical decisions
inform the checklist; they do not change Audit 1's independent findings above.
