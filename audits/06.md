# Audit 06 — complete workflow and adversarial reliability review

Reviewed 2026-10-20. Baseline: **0.18.0**, commit
`7990ff22cd9c1a411624452c5c618efe7a989d43`, initially clean working tree.
Remediation: **0.18.1**, uncommitted changes accompanying this report.

## Assessment

**The four-operation package is coherent and works for its documented original-
segment workflow. It is not a general converter for arbitrary EarthScope
MiniSEED downloads.** That distinction is the most consequential remaining
issue for the intended audience. EarthScope retrieval and original acquisition
identity are different boundaries; GeoCSV matching cannot undo archive changes.

No wrong-row association or coordinate contamination was demonstrated on the
tracked real examples. Matching ambiguity, fresh attachments, unit checks,
exact counts, and validation before batch mutation are substantive strengths.
The reader preserves the documented MERMAID data model, rather than claiming
universal GeoCSV conformance. Fetching verifies bytes against a release manifest.
SAC comparisons cover specified headers, not complete automaid reconstruction.

The review did reproduce export data-loss cases and two association validation
holes. These are patched below. The extreme numeric and long-code examples
are adversarial counterexamples, **not observed defects in the real MERMAID
fixture population**. No P0 defect was established.

The following findings are ordered by importance to the stated end-user goal.
P1 denotes scientific-integrity risk; P2 denotes workflow/contract correctness;
P3 denotes maintenance or verification limitations. A policy decision is not
classified as a newly discovered implementation bug merely because it limits
coverage.

**P2, high practical importance — decision retained for discussion; public
boundary clarified.**

`associate` requires the complete original SNCL, a sufficiently close start,
exact original count, and a compatible rate. A request boundary can trim an
acquisition. Archive responses or MiniSEED assembly can expose a longer trace,
a different segmentation, or overlaps whose sample selection is unknown.
These cases can fail correctly even when users downloaded the right station
and dates. Quality M alone neither proves a merge nor identifies an original.

The tracked P0045 example establishes that two original REQ segments can be
merged and receive `first_segment` with an explicit 25 ms tolerance. It does
not establish that arbitrary service responses can be handled. In particular,
`write_sac` deliberately rejects this association. The end-to-end path therefore
stops before SAC for some longer traces that can receive a location.

**Action taken:** README now states the archive/segment boundary, lack of merged
SAC export, and pending production hosting prominently. No reconstruction,
trimming, count relaxation, quality filtering, or merged-export policy was
introduced.

**Decision needed:** Is original-segment SAC export the intended supported
product? If yes, retain this narrow contract and describe unsupported downloads
as expected failures. If users must convert arbitrary EarthScope windows,
first choose a specific real archive case and the scientific meaning of its
output. Do not automatically add a general reconstruction API. Allowing anchor
coordinates in longer SAC files would be a separate mapping decision, especially
for pressure, depth, and lineage.

## 2. SAC serialization could change scientific values without raising

**P1, conditional numeric-integrity defect — fixed.**

Baseline public-API probes produced:

| Input accepted by association/export validation | Baseline SAC result |
| --- | --- |
| Four finite float64 samples equal to `1e100` | Four infinite float32 samples; call returned successfully |
| Complex samples `1+2j` | Imaginary components discarded; real samples written |
| Finite WaterPressure `1e100` mbar | Infinite `stdp` |
| Matched positive sample rate `1e100` Hz | Stored `delta=0` |
| NaN samples | NaN payload accepted without an explicit export policy |

NumPy warnings did not prevent successful output creation. Ordinary float32
rounding is expected; changing finite values to infinity or erasing nonzero
values to zero is a materially different failure. Complex input is outside
original MiniSEED scope but previously passed this boundary as well.

**Implemented:** export requires finite real samples; rejects sample overflow
and nonzero-to-zero underflow; validates float32 storage of delta, calibration,
depth and the calculated end offset; and rejects calibration values that would
serialize as SAC's undefined sentinel. Positive pressure that underflows during
the division is rejected too. Validation precedes output creation. Normal
float32 quantization remains supported, including the existing integer
16,777,217 -> 16,777,216 example.

A related probe showed that NumPy's float32 mean can overflow even when every
sample is representable. Export now lets ObsPy compute summaries from the
quantized sample values held in float64, preserving a finite mean for arrays
at the float32 maximum. This uses temporary waveform buffers, not a streaming
exporter. Original trace arrays are unchanged.

**Verification:** focused regressions cover these failures, nonfinite input,
underflow, near-sentinel calibration, finite maximum samples, no file creation
on rejection, and all 18 independent real SAC comparisons. Tutorial companions
and public docstrings describe the stricter input contract. This deliberately
rejects nonfinite input instead of silently exporting sample gaps.

**P2, existing policy and usability tradeoff — decision retained.**

Only **2 of 18** sampled original MiniSEED fixtures associate under the default
100 microseconds. Their waveform-minus-GeoCSV start residuals range from
30,000 to 971,000 ns. All 18 match with the already documented explicit 1 ms
tolerance. This agrees with the inspected automaid writer's millisecond
rendering, but does not measure physical clock accuracy. The current examples
already supply the override; a user relying on defaults can reasonably be
surprised.

Separately, the 0.01 Hz rate threshold is intentionally provisional. The
largest measured source/trace rate difference in these 18 examples is only
about **0.00000125 Hz**. The allowed threshold is substantially larger and
checks compatibility, not sample-grid equivalence. For illustration, 3,000
samples at 2.5 versus 2.50999 Hz have last-sample durations differing by about
4.77 seconds while satisfying that rate policy. The stricter fallback checks
last-sample alignment; the ordinary one-segment match does not.

`write_sac` reuses the source-rate agreement test. A small rate edit after
association can still pass, as can filtering or replacing samples without
changing matching headers. This is documented; `one_segment` is not an
integrity seal or proof of an untouched acquisition.

**No policy changed.** Decide separately whether to retain conservative defaults
with a standard 1 ms recipe, change the time default, tighten measured-rate
agreement, or record an association-time waveform snapshot for export checks.
A sample hash would answer a different question from scientific matching and
should not be added without a demonstrated need. Do not infer timing accuracy
from the number of printed digits or from ObsPy's rate-derived endtime.

## 4. SAC identity could be truncated

**P2, conditional output-contract defect — fixed.**

A matched station `ABCDEFGHI` was exported as `ABCDEFGH`. Non-ASCII station
text raised an uncontextualized encoding exception instead. Ordinary MiniSEED
2 codes fit the relevant SAC fields, so these probes do not establish a failure
in the sampled original inputs; they expose an unchecked serialization limit.

**Implemented:** the four identity fields must fit eight ASCII bytes without
surrounding whitespace or the reserved `-12345` token. Known empty Location
still works. Rejection happens before output creation. Tests cover long,
non-ASCII, padded, and undefined-token identities. No identity is renamed or
truncated to force an export.

## 5. Empty traces and truthy strings bypassed intended validation

**P2 — fixed.**

A trace with no samples and a source event with `SampleCount=0` received a
successful `one_segment` association. An empty waveform has no first sample
at which to assign the documented receiver position. Exact equality alone
was insufficient.

Passing `allow_first_segment="False"` enabled the fallback because a nonempty
string is truthy. This is an especially undesirable failure for an explicit
scientific opt-in.

**Implemented:** empty traces raise before any batch attachment; the fallback
flag must be a Python bool and other types raise TypeError. Tests verify an
empty member leaves a mixed Stream unchanged and strings/integers cannot
enable the fallback. Public signatures and valid bool behavior are unchanged.

## 7. Provenance and uniqueness have deliberate trust boundaries

**Resolved, 2026-10-21:** The user accepts the documented trust boundaries.
Association provenance is guaranteed only in the in-memory attachment at initial
association. Persistence beyond that attachment is the user's responsibility;
users may write sidecars in whatever format suits their workflow. The package
provides no sidecar format, writer, round-trip guarantee, or authentication of
user-written provenance. No additional persistence mechanism is planned for v1.
The existing source-table, mutability and uniqueness limits below remain.

**P2, documented scope — accepted.**

- Uniqueness means one eligible row among the **supplied** tables. Small subsets
  cannot establish uniqueness across omitted source history. Tests retain
  subset-to-original maps; the separate corpus check verifies all 18 expected
  associations against complete histories.
- Missing or naive event starts are ineligible, not proof that those records
  could not describe the waveform. A successful match does not certify every
  record in the source history. Invalid identities and duplicate complete
  matching keys do fail source preflight as documented.
- Parsed DataFrames and `stats.geocsv` row snapshots remain mutable. Immutable
  dataset declarations do not authenticate later row edits. Preserve original
  indices and metadata; do not reset indices, concatenate disparate histories,
  or manually change attached values and still claim original-file provenance.
- A bare local path records a resolved path, not a content checksum. Fetch
  provenance includes the verified checksum and exact manifest. Metadata need
  not survive pandas exports, and SAC does not serialize GeoCSV provenance.

These are reasons to keep source tables/download manifests with research
outputs, not reasons to introduce a provenance database or tamper-proof model.
User-managed sidecars remain outside the package contract; none is required
or created by the package.

## 8. Geographic SAC output is not calibrated or fully reconstructed automaid SAC

**Resolved, 2026-10-21:** The user confirms raw counts only for SAC waveform
samples. Instrument correction, response removal and counts-to-pressure
calibration are outside this repository's scope. The writer expects
uncalibrated MiniSEED-derived samples and preserves those values subject to
SAC float32 storage. It does not determine or undo processing performed before
input. Existing geographic mappings and missing-pressure rules are accepted;
no whole-automaid-header reconstruction is promised. This is a scope decision,
with no functional change.

**P2, scientific interpretation — accepted.**

The implemented four fields are latitude, longitude, sea-level `stel=0`, and
approximate depth `stdp=WaterPressure[mbar]/100`. The division reproduces
automaid's convention; it is not an oceanographic depth calculation. Missing
REQ pressure leaves depth undefined, while missing DET pressure fails.
Receiver elevation zero does not mean the submerged hydrophone is physically
at the surface. A source quality D selects the missing-pressure exception;
native waveform M/Q/D does not supply missing pressure or disambiguate rows.

MiniSEED's native calibration remains authoritative. The package does not
reconstruct automaid's counts-to-Pa factor, sensor response, orientation,
trigger values, user headers, or complete processing history. Finite SAC
precision and ObsPy's default SAC sample-interval rounding on read are further
reasons not to promise full header/rate equality. Existing tests correctly use
`round_sampling_interval=False` when comparing the conventional conversion.

**Action:** README now states lack of response correction/calibration and
serialized GeoCSV provenance. No mappings or physical models were expanded.
Keep these limitations in publication/website language as well.

## 9. Fetching is ready for its provisional protocol, not deployed hosting

**P2, external dependency — tabled by the user on 2026-10-21; revisit when hosting is ready.**

The client pins one release, validates inventory before downloads, preserves
selection order, verifies SHA-256/size, rejects path-component traversal,
refuses conflicting outputs, reuses identical files, and cleans failed
payload temporaries. A later batch failure leaves previously verified disk
files and the manifest; it returns no partial result list. Memory batches
return only on total success. These behaviors are documented and tested.

Remaining prerequisites are a real collection URL, immutable publication
procedure, stable instrument identifiers/inventory, retention of old releases,
and agreement between publisher and client on the manifest protocol. The
package requires an explicit base URL and does not pretend these exist.
Checksums establish agreement with a manifest, not publisher authenticity;
production examples should use HTTPS.

Socket timeouts are not whole-batch deadlines. There are no retries, offline
manifest discovery, release signatures, or compressed payload support. Those
are acceptable limits for this focused client. Keep collections in distinct
output roots when release IDs can collide. Disk SAC output can remain partial
on an I/O failure; a user loop over exports is not a batch transaction. These
are documented operational limits, not demonstrated reasons for a new job or
transaction framework.

## 10. Reader restrictions are explicit; generic GeoCSV compatibility remains limited

**Resolved, 2026-10-21:** The user confirms that MERMAID-specific format details,
including missing-value spellings such as `nan`, are not yet formally codified.
Retain the current documented reader rules as the package contract. Support is
for the documented MERMAID GeoCSV conventions; successful parsing is not a
certification of arbitrary GeoCSV producers or container versions. Formal
format questions remain open independently of closing this audit item. Future
authoritative clarification requires an explicit reconciliation of documentation,
tests and behavior; no parser behavior changes here.

**P3 for this MERMAID goal — documented scope accepted.**

The bundled v2.0.4 specification does not settle all current parser policies.
The reader intentionally reserves case-insensitive `nan`, treats empty cells
as missing except string Location, restricts datetime syntax/precision, requires
unique nonempty names and correctly sized metadata lists, and rejects missing
final line endings. Naive timestamps remain naive; a UTC unit does not infer
a timezone. Parsed values are typed representations, not a byte-for-byte
archive of every raw cell.

Dataset values merely containing `GeoCSV` are accepted without validating a
container version. Unknown repeated keyword changes use the documented
provisional boundary policy. These limitations are already recorded in
`OPEN_QUESTIONS.md`; none was silently reinterpreted during this audit.

The five printed specification examples still have three accepted examples
and two expected declaration-width rejections. An additional deterministic
probe preserved all **1,050 generated three-column records** across seven
delimiters, including Unicode, quotes, hash characters and multiline cells.
No new reader record-loss defect was established. This does not certify all
GeoCSV producers, ISO 8601 forms, pandas versions, or malformed-input extremes.
